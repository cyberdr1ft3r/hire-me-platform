# Issue #131 — Accounting raw-ID and source audit

Preflight audit for the Accounting V1 workspace, run against `main` `696a539` (after Commercial V1, PR #130). It covers the legacy `/accounting` panel in `apps/web/src/App.tsx`, `apps/web/src/api.ts`, `packages/contracts/src/accounting.ts`, `apps/api/src/accounting/*`, and the PostgreSQL accounting suite.

## Backend facts the UI must preserve

- Payments and the payment list need `payments:view`; the list is empty without `clients:view`, and a payment detail is client-scoped. Every financial write needs its capability plus `commercial_data:access`. Correction needs `payments:correct` and a reason, and cannot go below the allocated amount.
- Allocation needs `payments:manage`, `commercial_data:access`, and `invoices:view`. The invoice must be ISSUED, not archived, and in the same client and currency, and must pass client plus mission scope. Partial allocation is modeled: an allocation cannot exceed the payment's unallocated amount or the invoice's remaining balance. Reversal keeps the row and needs a reason. An idempotency key is optional.
- Invoice settlement (`GET /v1/accounting/invoices/:id/settlement`) needs `invoices:view` and `payments:view`, and derives UNPAID, PARTIALLY_PAID, PAID, OVERDUE, or NOT_RECEIVABLE on the server.
- Expense contexts are four optional typed links (client, recruitment mission, placement, training program), validated as one consistent chain. An expense is readable only when every linked context passes its own source scope.
- Client receivables and the overdue list need `client_balances:view` and `commercial_data:access`, and are computed per currency on the server. Profitability needs `profitability:view` and `commercial_data:access` for one CLIENT, RECRUITMENT_MISSION, or PLACEMENT context, and returns issued-invoice revenue minus linked expenses per currency (D-053). It is not a P&L.
- Amounts, correction or reversal reasons, the vendor, and the description are null without `commercial_data:access`.
- The Commercial invoice list (`GET /v1/commercial/invoices`) applies exactly the Accounting invoice scope (`clients:view`; mission-linked invoices only with `missions:view` and an active assignment, or `mission_candidates:transfer`).
- The Training program list applies exactly the Accounting training mirror (`visibleTrainingProgramScope`).

## Prerequisite (D-081)

The smallest bounded Accounting-specific source:

- `payment.display = { clientName }`;
- `allocation.display = { invoiceReference | null, paymentReference }`, where the invoice reference is resolved through the Accounting invoice scope in the database predicate;
- `expense.display = { clientName, missionTitle, placement: { missionTitle, integrationStartDate, confirmedAt } | null, trainingProgramName }`;
- overdue `row.display = { clientName }`;
- `GET /v1/accounting/placement-options?recruitmentMissionId=`. The route requires `placements:view`; the service requires `commercial_data:access` and either `profitability:view` or `expenses:manage`, then applies the placement mission scope. It returns at most 20 non-archived placements of one mission, with no count and no candidate identity.

There is no migration and no new permission, and `FINANCE_MANAGER` grants are unchanged. Under the unchanged server rules, the Finance Manager works with client-only contexts: no mission, placement, or training context, and no reference for an allocation to a mission-linked invoice. This is consistent with R-050.
